## 4. Original IA-01 reproduction

Independently loaded the parent utility using `git show HEAD^:projects/ui-core/rich-text-editor/neu-rich-text-editor.utils.ts`, compiled it in memory with TypeScript and evaluated it in an isolated VM. No checkout or source substitution was performed.

Input:

```html
<a href="https://example.test/?a=1&amp;b=2"
   title="A &amp; B">link</a>
```

The parent produces `&amp;amp;` on the first pass and further growth on the second. Real Chromium parses its result as query keys `a,amp;b`, with `get('b') === null` and title `A &amp; B`. Thus the old implementation independently fails the actual semantic expectation, not merely an output snapshot.

## 5. Current reproduction result

The same in-memory probe against HEAD produces canonical `&amp;`, not `&amp;amp;`. Real Chromium reports:

- `anchor.href === 'https://example.test/?a=1&b=2'`;
- query keys exactly `a,b`, with values `1,2`;
- `anchor.title === 'A & B'`.

An independent 17-case old/current Chromium matrix covered the exact reproduction, four entity forms, deliberate literal entity text, six rejected protocol forms and four insertion-construction variants. Expected semantic values were literal constants, not generated by the sanitizer under test.

## 6. Idempotence

For the original counterexample, `once === twice === third` at HEAD. The four supported ampersand forms also reach stable canonical output. The committed utility tests separately exercise repeated sanitization. This is a bounded claim for the verified contract cases, not universal equivalence to an HTML5 parser.

## 7. Named/numeric entity handling

Independently checked `&amp;`, `&#38;`, `&#x26;` and `&#X26;` in href, title and alt. They yield the same browser meaning and canonical output. Committed tests additionally cover quote, angle-bracket and apostrophe references and an encoded safe HTTPS colon.

Decoding is one layer only: source `&amp;amp;` remains canonical `&amp;amp;`, with actual attribute value containing literal `&amp;`. It is not recursively changed to an ampersand separator. The deliberate literal case must not be confused with IA-01's accidental extra encoding.

## 8. Unsafe encoded protocols

Independent probes reject `javascript&#58;alert(1)`, `javascript&#x3A;alert(1)` and `javascript&#X3A;alert(1)` for both link href and image src. Also checked an encoded letter in `java&#115;cript:alert(1)`, a non-image data URL and VBScript. No corresponding href/src or injected event-handler attribute survived.

The three required encoded-colon variants also pass the committed directed security tests.

## 9. Validation order

Source inspection confirms raw attribute source → `decodeRichTextAttribute` → existing URL/image/attribute validation → `escapeRichTextAttribute` for serialization. The decoder does not bypass the validator or replace the escaping step. Its single replacement pass does not recursively decode returned text.

The only change at the call site is decoding the captured attribute value before the existing checks. Tag/attribute allowlists and protocol validators are unchanged from the parent.

## 10. Title/alt semantics

Actual Chromium DOM title and image alt are `A & B` for each of the four entity forms. Committed pure tests cover the other supported textual references. Title and alt use the same private attribute path; no Angular, TemplateRef, DOM metadata or locale-dependent decoder is introduced.

## 11. Link insertion

Reviewed actual `addLink()` → construction escaping → `insertHtml()` sanitization → native editor/value synchronization. The real component's directed insertion test passes for an ampersand-bearing URL. Its execCommand implementation is mocked in the unit test; that test alone is not treated as real browser editing evidence.

Independent construction-path probes parsed the resulting HTML in Chromium for raw `&`, literal double quotes, literal `&amp;` and literal `&#34;` in prompt URL strings. `getAttribute('href')` preserves those semantic input strings, with only href/target/rel attributes. Literal entity text supplied through a prompt is plain URL text, not pre-parsed HTML. Quotes remain inside the URL rather than creating attributes.

Additional adversarial observation: `https://example.test/?q=" onmouseover="alert(1)&b=2` becomes `<a>link</a>` under both parent and current code. The pre-existing global lexical event-handler removal also matches attribute-like text inside that constructed URL. An initial exploratory expectation of URL preservation failed; direct parent comparison proved identical behavior before REM-03. No handler was injected. This is a pre-existing parser compatibility limitation, outside the demonstrated IA-01 entity repair, not a new REM-03 P0/P1 or a claim of general safe-URL preservation. No fix was made.
