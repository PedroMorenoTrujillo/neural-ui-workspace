# Naming y API — Ledger Neural UI 2

Auditoría estática del working tree `v2` sobre `a6a9606613fba61e7c337c3f57d1aecbb11702e8`, con Fases 1, 2 y 3A acumuladas. Consulta de fuentes: 12 de septiembre de 2026. Prime de referencia: **22.1.1**. Las propuestas describen arquitectura futura; no están implementadas. PARITY significa cobertura del caso indicado por fuente/contrato y tests existentes, no una certificación comparativa de ejecución. Los gates históricos se atribuyen a su fase; no se volvieron a ejecutar en esta auditoría.

## Principio rector — enmienda Neural UI 2

**PrimeNG es exclusivamente baseline funcional y competitivo. Su naming, inputs, outputs, estado y arquitectura no son el target.** Para cada caso: «¿Cuál es la solución Neural más simple, reactiva, eficiente, coherente y Angular 22-native para cubrirlo o superarlo?» Neural UI 2 es un major: se autorizan renames, fusiones, eliminaciones, cambios de eventos/estado y reescrituras completas. Neural UI 1 conserva el contrato antiguo; Neural UI 2 no incluye aliases, wrappers o compatibility layers para evitar el breaking.

Priorizar simplicidad conceptual, signals como estado real, input/model/computed cuando proceda, tipos fuertes, API expresiva, menos estado duplicado y código imperativo. Zoneless, SSR/hydration, accesibilidad, lifecycle/memoria, tree-shaking, bundle, rendimiento, mantenibilidad y coherencia transversal son gates del diseño. Ninguna API nueva se justifica solo por modernidad. Menor configuración, DOM, listeners, effects o duplicación puede ser superioridad objetiva si se mide manteniendo la capacidad.

Las conversiones de datos de migración son operaciones puntuales del consumidor, no compatibilidad embebida en el paquete. La integración con HTTP, URL o almacenamiento es un límite externo legítimo que seguiría existiendo en una app nueva; no debe emular APIs Prime ni sostener estado espejo. Cada decisión requiere beneficio concreto y prueba; ni conservar ni reescribir código antiguo es un fin en sí mismo.

## Sistema propuesto

Model de formulario: value o checked. Estado aplicado: sustantivo de dominio (query, selectedKeys, expandedKeys, activeId, collapsed). Output `XChange`: propuesta del nuevo estado, salvo model de formulario que representa escritura del dato. Intención de operación: `XRequested` o nombres consolidados dataRequest/childrenRequest/suggestionsRequest. Lifecycle: opened/closed después del hecho. Detalle: evento específico solo si añade fuente, opción o resultado.

No copiar onX de Prime ni anteponer neu a outputs. API pública de Angular se mide por publicName/alias, no por nombre TypeScript. Un signal público no es input ni model. Options son configuración estable; no esconder estados y callbacks heterogéneos en un único options:any. Boolean simple se mantiene si solo hay dos comportamientos válidos.

## Convenciones de tipos, igualdad y configuraciones

Colecciones readonly; empty=[] y scalar optional=null. Generic T representa entidad/option; V valor; K identidad. Cada callback tiene contexto tipado y Event nativo opcional cuando la acción puede ser programática. No añadir Event ficticio. `rowKey` y compareWith se documentan por semántica, no se fusionan por compartir función.

Inputs visuales: tone se limita a neutral/info/success/warning/danger cuando el componente realmente tiene esas intenciones; variant expresa solid/outline/ghost u otras presentaciones existentes. El implementador produce mapping exacto por componente y token antes del rename P2; no imponer una unión universal imposible. `type` en Input/DateInput sigue dominio nativo. `readonly` de Forms conserva el nombre Angular oficial; atributos HTML y nombres de framework no son deuda de naming.

## Controlado y no controlado

Cada slice declara owner. Si input aplicado existe, user action propone y el consumidor acepta/rechaza. Si falta, initialX inicializa una vez y el componente mantiene estado. Cambiar entre modos durante vida de instancia requiere política explícita y test. No usar model en una slice con rechazo obligatorio: el model modifica estado local antes de la aceptación. Draft de editor/filtro, índice activo y overlay son estados efímeros diferentes; tenerlos no es duplicidad por sí mismo.

## Inventario de migración obligatorio

Antes de retirar cualquiera de las APIs, generar ledger del public-contract actual y target con: selector/entrypoint, publicName, firma vieja/nueva, acción, default, temporalidad, ejemplo y test consumer. Todas las entradas de 80/38 de Table,49/25 TreeTable y 1496 bindings globales deben acabar en KEEP o cambio explícito. Este documento especifica decisiones; el diff exhaustivo de firmas se genera al implementar, sin modificar manifests en la auditoría.

Aliases de metadata legítimos permanecen. Aliases de compatibilidad retirados no se vuelven a crear para renombrar por segunda vez. Cambios de temporalidad se migran por semántica: Dialog closed antiguo→closeRequested y hidden→closed en un mismo consumer. El paquete2 final no conserva ambos setters de una misma slice para ocultar errores de migración.

## Gate de simplicidad de API major

Cada rename/fusión/eliminación debe responder: qué concepto simplifica, qué owner desaparece, qué capacidad conserva, qué coste reduce y cómo se verifica. Un alias público puramente legacy se retira con todos sus usos; un nombre TypeScript distinto del único publicName Angular no es un alias duplicado para el consumidor. La retirada de tokens de compatibilidad forma parte del contrato2, aunque el rediseño visual más amplio sea P2.

No se exige mantener métodos, selectors o configuraciones1.x como interfaz de la nueva implementación. El registry de API target se escribe desde conceptos Neural; la matriz Prime solo demuestra cobertura de casos. Las guías muestran conversión una vez; el paquete no incorpora una capa de inputs Prime ni traduce en cada render estados viejos al nuevo.
